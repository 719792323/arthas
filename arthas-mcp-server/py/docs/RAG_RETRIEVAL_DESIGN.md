## 1. 系统总览

本系统采用 **"向量语义检索 + BM25 关键词检索"双路混合**，通过 **RRF（Reciprocal Rank Fusion）** 融合两路结果，
再经过 **Parent-Child 双层索引**的 Child→Parent 映射，返回上下文完整的知识片段给 LLM。

核心思想：**用小 chunk 检索（语义精准），返回大 chunk 回答（上下文完整）**。

```
用户查询
   │
   ├──→ [向量语义检索] ──→ child chunks + scores
   │                                │
   └──→ [BM25 关键词检索] ──→ child chunks + scores
                                    │
                            ┌───────▼────────┐
                            │  RRF 分数融合   │
                            └───────┬────────┘
                                    │
                            ┌───────▼────────┐
                            │ Child → Parent  │
                            │ 映射 + 聚合去重  │
                            └───────┬────────┘
                                    │
                            ┌───────▼────────┐
                            │ Token 预算截断   │
                            └───────┬────────┘
                                    │
                                返回 parent chunks
```

## 2. BM25 检索原理

### 2.1 什么是 BM25

BM25（Best Matching 25）是一种经典的 **基于词频的文本相关性打分算法**，属于 TF-IDF 家族的改进版本。
它的核心思想是：**一个词在某篇文档中出现得越频繁，同时在整个语料库中出现得越稀少，那么这个词对这篇文档的相关性贡献就越大**。

### 2.2 BM25 公式

对于查询 Q 包含的关键词 q₁, q₂, ..., qₙ，文档 D 的 BM25 得分为：

```
BM25(D, Q) = Σᵢ IDF(qᵢ) × TF(qᵢ, D)
```

其中：

**IDF（逆文档频率）**——衡量词的稀缺程度：
```
IDF(q) = log((N - n(q) + 0.5) / (n(q) + 0.5) + 1)

N = 语料库中的文档总数
n(q) = 包含词 q 的文档数
```
> 含义：一个词出现在越少的文档中，IDF 值越高，说明它越有区分度。比如 "thread" 如果只出现在 1 篇文档中，IDF 就很高；而 "命令" 在几乎所有文档中都出现，IDF 就很低。

**TF（词频因子）**——衡量词在当前文档的出现频率，但做了饱和处理：
```
TF(q, D) = f(q, D) × (k₁ + 1) / (f(q, D) + k₁ × (1 - b + b × |D| / avgdl))

f(q, D) = 词 q 在文档 D 中的出现次数
|D| = 文档 D 的长度（词数）
avgdl = 语料库中文档的平均长度
k₁ = 1.5（词频饱和参数，控制词频增长的边际递减速度）
b = 0.75（文档长度归一化参数）
```
> 含义：词频越高得分越高，但增长逐渐饱和（出现 10 次不会比出现 5 次高很多）。同时，较长的文档会被适当"惩罚"，避免长文档因为词多而占优势。

### 2.3 BM25 在本项目中的实现

本项目使用 `rank-bm25` 库的 `BM25Okapi` 实现，配合 `jieba` 中文分词：

```
构建索引阶段：
  child chunk 文本 → jieba 分词 → 构建 BM25Okapi 倒排索引

检索阶段：
  用户查询 → jieba 分词 → BM25Okapi.get_scores() → 按分数降序返回 top_k
```

代码对应关系（`bm25_index.py`）：
- `_tokenize()`: 使用 jieba.lcut 精确模式分词，过滤空白和标点
- `BM25Index.build()`: 对所有 child chunk 分词后构建 BM25Okapi 实例
- `BM25Index.search()`: 对查询分词后调用 get_scores()，过滤 score > 0 的结果

### 2.4 BM25 完整数值计算示例

为了彻底弄清楚 BM25 怎么给文档打分，下面用一个**可以手算的极简例子**走一遍完整流程。

#### 场景设定

假设我们的知识库只有 **3 个 child chunk**（即 BM25 的 3 篇"文档"）：

| 文档编号 | chunk_id | 原始内容 | jieba 分词结果 | 词数 \|D\| |
|---------|----------|---------|---------------|-----------|
| D0 | abc123_0 | `# thread 命令` `## 基本用法` `使用 thread 命令 可以 查看 当前 所有 线程 的 运行 状态 和 CPU 使用率` | ["thread", "命令", "基本", "用法", "使用", "thread", "命令", "可以", "查看", "当前", "所有", "线程", "运行", "状态", "CPU", "使用率"] | 16 |
| D1 | abc123_1 | `# thread 命令` `## CPU 排查` `当 发现 Java 进程 CPU 占用 过 高 时 可以 使用 thread -n 3 查看 CPU 使用率 最高 的 3 个 线程 的 堆栈 信息` | ["thread", "命令", "CPU", "排查", "发现", "Java", "进程", "CPU", "占用", "高", "可以", "使用", "thread", "查看", "CPU", "使用率", "最高", "线程", "堆栈", "信息"] | 20 |
| D2 | abc123_2 | `# thread 命令` `## 死锁检测` `使用 thread -b 可以 检测 当前 JVM 中 是否 存在 死锁` | ["thread", "命令", "死锁", "检测", "使用", "thread", "可以", "检测", "当前", "JVM", "是否", "存在", "死锁"] | 13 |

统计参数：
```
N = 3（文档总数）
avgdl = (16 + 20 + 13) / 3 = 16.33（平均文档长度）
k₁ = 1.5
b = 0.75
```

#### 用户查询

```
查询："CPU 排查"
jieba 分词 → ["CPU", "排查"]
```

需要为每个文档计算 BM25 分数，公式：**BM25(D, Q) = IDF("CPU") × TF("CPU", D) + IDF("排查") × TF("排查", D)**

---

#### Step 1：计算每个查询词的 IDF

**词 "CPU"：**
```
n("CPU") = 包含 "CPU" 的文档数
  D0: 出现了 "CPU" → ✅
  D1: 出现了 "CPU" → ✅
  D2: 没有 "CPU"   → ❌
  n("CPU") = 2

IDF("CPU") = log((N - n + 0.5) / (n + 0.5) + 1)
           = log((3 - 2 + 0.5) / (2 + 0.5) + 1)
           = log(1.5 / 2.5 + 1)
           = log(0.6 + 1)
           = log(1.6)
           = 0.470
```

**词 "排查"：**
```
n("排查") = 包含 "排查" 的文档数
  D0: 没有 "排查" → ❌
  D1: 出现了 "排查" → ✅
  D2: 没有 "排查" → ❌
  n("排查") = 1

IDF("排查") = log((3 - 1 + 0.5) / (1 + 0.5) + 1)
            = log(2.5 / 1.5 + 1)
            = log(1.667 + 1)
            = log(2.667)
            = 0.981
```

> 💡 **关键观察**："排查" 的 IDF（0.981）远高于 "CPU" 的 IDF（0.470），因为 "排查" 只出现在 1 篇文档中，区分度更高。

---

#### Step 2：计算每个文档中每个查询词的 TF

TF 公式：`TF(q, D) = f(q, D) × (k₁ + 1) / (f(q, D) + k₁ × (1 - b + b × |D| / avgdl))`

**文档 D0（基本用法，|D|=16）：**
```
f("CPU", D0) = 1（"CPU" 在 D0 中出现 1 次）

TF("CPU", D0) = 1 × (1.5 + 1) / (1 + 1.5 × (1 - 0.75 + 0.75 × 16/16.33))
              = 2.5 / (1 + 1.5 × (0.25 + 0.75 × 0.9798))
              = 2.5 / (1 + 1.5 × (0.25 + 0.7349))
              = 2.5 / (1 + 1.5 × 0.9849)
              = 2.5 / (1 + 1.4773)
              = 2.5 / 2.4773
              = 1.009

f("排查", D0) = 0（"排查" 在 D0 中不出现）
TF("排查", D0) = 0  ← 词频为 0，TF 直接为 0
```

**文档 D1（CPU 排查，|D|=20）：**
```
f("CPU", D1) = 3（"CPU" 在 D1 中出现 3 次！）

TF("CPU", D1) = 3 × 2.5 / (3 + 1.5 × (0.25 + 0.75 × 20/16.33))
              = 7.5 / (3 + 1.5 × (0.25 + 0.9184))
              = 7.5 / (3 + 1.5 × 1.1684)
              = 7.5 / (3 + 1.7526)
              = 7.5 / 4.7526
              = 1.578

f("排查", D1) = 1

TF("排查", D1) = 1 × 2.5 / (1 + 1.5 × (0.25 + 0.75 × 20/16.33))
               = 2.5 / (1 + 1.7526)
               = 2.5 / 2.7526
               = 0.908
```

**文档 D2（死锁检测，|D|=13）：**
```
f("CPU", D2) = 0 → TF = 0
f("排查", D2) = 0 → TF = 0
```

> 💡 **关键观察**：D1 中 "CPU" 出现了 3 次，但 TF 只有 1.578（而不是 D0 的 1.009 的 3 倍）。这就是 BM25 的**词频饱和**效果——出现 3 次和出现 1 次的差距没那么大。

---

#### Step 3：最终得分

```
BM25(D0, Q) = IDF("CPU") × TF("CPU", D0) + IDF("排查") × TF("排查", D0)
            = 0.470 × 1.009 + 0.981 × 0
            = 0.474 + 0
            = 0.474

BM25(D1, Q) = IDF("CPU") × TF("CPU", D1) + IDF("排查") × TF("排查", D1)
            = 0.470 × 1.578 + 0.981 × 0.908
            = 0.742 + 0.891
            = 1.633  ✅ 最高分

BM25(D2, Q) = 0 + 0 = 0（两个词都不出现，直接过滤）
```

#### 最终结果

```
BM25 检索返回（按 score 降序，过滤 score ≤ 0）：

  rank 1: abc123_1 (CPU 排查)    score = 1.633
  rank 2: abc123_0 (基本用法)    score = 0.474
  （abc123_2 因 score = 0 被过滤掉）
```

#### 为什么 D1 得分最高？拆解看看

| 因素 | D0 (基本用法) | D1 (CPU 排查) | D2 (死锁检测) |
|------|--------------|---------------|--------------|
| "CPU" 出现次数 | 1 次 | 3 次 ✅ | 0 次 |
| "排查" 出现次数 | 0 次 | 1 次 ✅ | 0 次 |
| "CPU" 的贡献 | 0.470 × 1.009 = 0.474 | 0.470 × 1.578 = 0.742 | 0 |
| "排查" 的贡献 | 0 | 0.981 × 0.908 = **0.891** ← 最大贡献 | 0 |
| **总分** | **0.474** | **1.633** | **0** |

> 💡 **核心结论**：D1 得分最高有两个原因：
> 1. "CPU" 出现了 3 次，TF 更高（但因为饱和效果，只比 D0 高 56%，而不是 300%）
> 2. "排查" 只出现在 D1 中，IDF 很高（0.981），这个词的贡献（0.891）反而是拉开差距的关键

这正好体现了 BM25 的核心直觉：**稀有词比高频词更重要**。

#### 对照代码实现

上面的手算过程对应到代码（`bm25_index.py`）：

```python
# 1. 构建索引阶段（build 方法）
tokenized_docs = [_tokenize(doc) for doc in documents]
#   等价于：tokenized_docs = [
#     ["thread", "命令", "基本", "用法", ...],   # D0
#     ["thread", "命令", "CPU", "排查", ...],     # D1
#     ["thread", "命令", "死锁", "检测", ...],    # D2
#   ]
bm25 = BM25Okapi(tokenized_docs)
#   BM25Okapi 内部自动计算了 N、avgdl、每个词的 n(q) 等统计量

# 2. 检索阶段（search 方法）
tokenized_query = _tokenize("CPU 排查")
#   等价于：["CPU", "排查"]
scores = bm25.get_scores(tokenized_query)
#   等价于：scores = [0.474, 1.633, 0.0]
#   然后过滤 score > 0，按降序返回 → [(abc123_1, 1.633), (abc123_0, 0.474)]
```

### 2.5 BM25 的优势与局限

| 维度 | 优势 | 局限 |
|------|------|------|
| 关键词精确匹配 | ✅ 对 "thread"、"watch"、"OOM" 等精确命令名/术语匹配极强 | ❌ 无法理解同义词（"线程"≠"thread"） |
| 计算开销 | ✅ 纯 CPU 计算，极快（毫秒级） | - |
| 语义理解 | ❌ 无法理解"怎么排查 CPU 高"和"thread 命令"的语义关联 | ❌ 完全基于字面匹配 |
| 长文档处理 | ✅ 自带文档长度归一化 | - |

因此 BM25 作为 **向量语义检索的补充路径**，增强对 Arthas 命令名、Java 类名等关键词的精确匹配能力。

## 3. 向量语义检索原理

向量检索将文本转换为高维向量（embedding），通过计算向量间的余弦相似度来衡量语义相关性。

```
"怎么排查 CPU 占用高的问题" → embedding → [0.12, -0.34, 0.56, ...]
                                                    ↓ 余弦相似度
"thread 命令用于查看当前线程信息和 CPU 使用率" → embedding → [0.15, -0.31, 0.58, ...]
```

本项目使用 `BAAI/bge-m3` 模型生成 embedding，通过 ChromaDB 存储和检索。

## 4. 混合检索与 RRF 融合

### 4.1 为什么需要混合

| 用户查询 | 向量检索效果 | BM25 效果 |
|---------|------------|----------|
| "怎么排查 CPU 高" | ✅ 语义匹配到 thread 命令文档 | ❌ 没有精确关键词命中 |
| "thread 命令" | 一般（语义太短） | ✅ 精确匹配到 thread 文档 |
| "thread CPU 排查" | ✅ 较好 | ✅ 较好 |

混合两路可以互补：**语义理解 + 精确匹配 = 更全面的召回**。

### 4.2 RRF 融合算法

RRF（Reciprocal Rank Fusion）是一种简单而有效的排名融合方法，**只关注排名位置，不关注原始分数**。

公式：
```
RRF_score(d) = Σ 1 / (k + rankᵢ(d))

k = 60（标准常数，本项目中 _RRF_K = 60）
rankᵢ(d) = 文档 d 在第 i 路检索中的排名（从 1 开始）
```

**示例：** 假设向量检索和 BM25 检索各返回 3 个结果：

```
向量检索结果（按相似度降序）：   BM25 检索结果（按 BM25 score 降序）：
  rank 1: c1 (score=0.92)        rank 1: c3 (score=8.5)
  rank 2: c2 (score=0.85)        rank 2: c1 (score=6.2)
  rank 3: c4 (score=0.78)        rank 3: c5 (score=3.1)
```

RRF 融合计算：
```
c1: 1/(60+1) + 1/(60+2) = 0.01639 + 0.01613 = 0.03252  ← 两路都命中，排名最高
c3: 0        + 1/(60+1) = 0.01639
c2: 1/(60+2) + 0        = 0.01613
c4: 1/(60+3) + 0        = 0.01587
c5: 0        + 1/(60+3) = 0.01587
```

融合后排序：**c1 > c3 > c2 > c4 = c5**

> c1 因为在两路检索中都被命中，RRF 分数最高——这就是 RRF 的精髓：**双路命中的文档自然获得更高排名**。

融合后会用 `rag_rrf_score_threshold`（默认 0.01）过滤掉低分结果。

## 5. Parent-Child 双层索引

### 5.1 设计思想

| 角色 | 粒度 | 用途 | 是否生成 Embedding |
|------|------|------|-------------------|
| **Child chunk** | 小（≤512 tokens） | 向量检索 + BM25 检索 | ✅ 是 |
| **Parent chunk** | 大（≤2048 tokens） | 返回给 LLM 作为上下文 | ❌ 否 |

为什么这么设计？
- **小 chunk 检索更精准**：embedding 语义更集中，不会被无关内容稀释
- **大 chunk 回答更完整**：LLM 需要足够的上下文才能给出准确回答

### 5.2 Child → Parent 映射与 Score 聚合

当多个 child chunk 命中同一个 parent 时，需要聚合去重。

聚合公式：
```
parent_score = max(child_scores) + α × (hit_count - 1) / total_children

α = 0.15（多命中加成系数，即 _MULTI_HIT_ALPHA）
hit_count = 该 parent 下命中的 child 数量
total_children = 该 parent 下的 child 总数
```

> 直觉：如果一个 parent 下有多个 child 都被检索命中，说明这个 parent 的整体相关性更高，应该获得额外加分。

## 6. 端到端流程示例

### 6.1 准备：一个 Markdown 知识文档

假设我们的知识库中有一篇文档 `thread.md`：

```markdown
# thread 命令

thread 命令是 Arthas 中用于排查线程问题的核心工具。

## 基本用法

使用 `thread` 命令可以查看当前所有线程的运行状态和 CPU 使用率。
执行 `thread` 不带参数会列出所有线程信息，按 CPU 使用率降序排列。

## CPU 排查

当发现 Java 进程 CPU 占用过高时，可以使用 `thread -n 3` 查看 CPU 使用率
最高的 3 个线程的堆栈信息。这是排查 CPU 高问题最常用的方式。

## 死锁检测

使用 `thread -b` 可以检测当前 JVM 中是否存在死锁。如果检测到死锁，
会输出死锁涉及的线程信息和等待关系。
```

### 6.2 索引构建阶段

**Step 1：MarkdownChunker 解析标题树**

```
root (level=0)
└── "thread 命令" (level=1)      ← heading_line: "# thread 命令"
    ├── body: "thread 命令是 Arthas 中..."
    ├── "基本用法" (level=2)      ← heading_line: "## 基本用法"
    │   └── body: "使用 thread 命令可以查看..."
    ├── "CPU 排查" (level=2)      ← heading_line: "## CPU 排查"
    │   └── body: "当发现 Java 进程 CPU..."
    └── "死锁检测" (level=2)      ← heading_line: "## 死锁检测"
        └── body: "使用 thread -b 可以..."
```

**Step 2：收集叶子节点**

叶子节点（没有子标题的节点）= `["基本用法", "CPU 排查", "死锁检测"]`

**Step 3：确定 Parent 边界**

对每个叶子节点向上查找 parent：
- "基本用法" → 向上找 "thread 命令"（level=1）→ 计算 full_text() 的 tokens
  - 假设 "thread 命令" 的 full_text() = 280 tokens < max_parent_size(2048) → ✅ 可以作为 parent
- "CPU 排查"、"死锁检测" → 同理，parent 都是 "thread 命令"

**Step 4：生成 Parent-Child 双层 Chunk**

```
┌─────────────────────────────────────────────────┐
│ Parent Chunk (chunk_id: "abc123_p0")            │
│                                                 │
│ # thread 命令                                    │
│ thread 命令是 Arthas 中用于排查线程问题的核心工具。│
│ ## 基本用法                                      │
│ 使用 thread 命令可以查看当前所有线程...            │
│ ## CPU 排查                                      │
│ 当发现 Java 进程 CPU 占用过高时...                │
│ ## 死锁检测                                      │
│ 使用 thread -b 可以检测...                       │
│                                                 │
│ metadata: {chunk_level: "parent",               │
│            total_children: 3}                   │
└─────────────────────────────────────────────────┘
      │
      ├── Child Chunk 0 (chunk_id: "abc123_0")
      │   ┌──────────────────────────────────────┐
      │   │ # thread 命令       ← 祖先标题前缀    │
      │   │ ## 基本用法                           │
      │   │ 使用 thread 命令可以查看当前所有线程... │
      │   │                                      │
      │   │ metadata: {chunk_level: "child",      │
      │   │   parent_chunk_id: "abc123_p0"}       │
      │   └──────────────────────────────────────┘
      │
      ├── Child Chunk 1 (chunk_id: "abc123_1")
      │   ┌──────────────────────────────────────┐
      │   │ # thread 命令       ← 祖先标题前缀    │
      │   │ ## CPU 排查                           │
      │   │ 当发现 Java 进程 CPU 占用过高时...     │
      │   │                                      │
      │   │ metadata: {chunk_level: "child",      │
      │   │   parent_chunk_id: "abc123_p0"}       │
      │   └──────────────────────────────────────┘
      │
      └── Child Chunk 2 (chunk_id: "abc123_2")
          ┌──────────────────────────────────────┐
          │ # thread 命令       ← 祖先标题前缀    │
          │ ## 死锁检测                           │
          │ 使用 thread -b 可以检测...            │
          │                                      │
          │ metadata: {chunk_level: "child",      │
          │   parent_chunk_id: "abc123_p0"}       │
          └──────────────────────────────────────┘
```

**Step 5：分别存储**

| 操作 | Parent Chunk | Child Chunk |
|------|-------------|-------------|
| 生成 Embedding | ❌ 不生成 | ✅ 生成 |
| 写入向量数据库 | ❌ | ✅ |
| 写入 BM25 索引 | ❌ | ✅ |
| 写入 ParentChunkStore | ✅（内存字典） | ❌ |

### 6.3 检索阶段

假设用户查询：`"怎么排查 CPU 占用高"`

**Step 1：双路检索**

```
┌─────────────── 向量语义检索 ───────────────┐
│ "怎么排查 CPU 占用高" → embedding           │
│ → 向量数据库近邻搜索（top_k * 3 = 9）       │
│                                            │
│ 结果（按余弦相似度降序）：                    │
│   rank 1: abc123_1 (CPU 排查)    score=0.91 │
│   rank 2: abc123_0 (基本用法)    score=0.78 │
│   rank 3: abc123_2 (死锁检测)    score=0.62 │
└────────────────────────────────────────────┘

┌─────────────── BM25 关键词检索 ──────────────┐
│ "怎么排查 CPU 占用高"                         │
│ → jieba 分词: ["怎么", "排查", "CPU", "占用", "高"] │
│ → BM25Okapi.get_scores()                     │
│                                              │
│ 结果（按 BM25 score 降序）：                    │
│   rank 1: abc123_1 (CPU 排查)    score=7.8   │
│   rank 2: abc123_0 (基本用法)    score=3.2   │
│   (abc123_2 的 score ≤ 0，被过滤)             │
└──────────────────────────────────────────────┘
```

**Step 2：RRF 融合**

```
abc123_1: 1/(60+1) + 1/(60+1) = 0.01639 + 0.01639 = 0.03279  ← 两路 rank 1
abc123_0: 1/(60+2) + 1/(60+2) = 0.01613 + 0.01613 = 0.03226  ← 两路 rank 2
abc123_2: 1/(60+3) + 0        = 0.01587                       ← 仅向量命中

过滤 rrf_score < 0.01 的结果 → 全部保留
融合排序：abc123_1 > abc123_0 > abc123_2
```

**Step 3：Child → Parent 映射 + Score 聚合**

三个 child 都指向同一个 parent `abc123_p0`：
```
parent "abc123_p0":
  max_score = 0.03279 (来自 abc123_1)
  hit_count = 3
  total_children = 3

parent_score = 0.03279 + 0.15 × (3 - 1) / 3
             = 0.03279 + 0.10
             = 0.13279
```

**Step 4：返回 Parent Chunk**

从 ParentChunkStore 取出 parent `abc123_p0` 的完整内容（包含"基本用法"、"CPU 排查"、"死锁检测"三个小节），经 Token 预算截断后返回给 LLM。

LLM 拿到的是**完整的 thread 命令文档**，而不是单独的 "CPU 排查" 片段——这样它能结合上下文给出更准确的回答。

### 6.4 如果 BM25 不可用会怎样？

系统自动降级为**纯向量检索**：
- 跳过 BM25 检索步骤
- 跳过 RRF 融合步骤
- 直接使用向量检索结果，按 similarity_threshold 过滤
- 后续的 Child → Parent 映射流程不变

降级是透明的，不会报错或阻断主流程。

## 7. 配置参数说明

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `rag_enabled` | `True` | 是否启用 RAG |
| `rag_knowledge_dir` | `"knowledge/"` | 知识库文档目录 |
| `rag_store_type` | `"chroma"` | 向量数据库类型 |
| `rag_top_k` | `3` | 检索返回的最大知识片段数 |
| `rag_similarity_threshold` | `0.5` | 纯向量检索时的相似度过滤阈值 |
| `rag_max_tokens` | `2048` | RAG 知识的 Token 预算上限 |
| `rag_embedding_model` | `"BAAI/bge-m3"` | Embedding 模型 |
| `rag_max_parent_size` | `2048` | Parent chunk 动态边界的 token 上限 |
| `rag_hybrid_search_enabled` | `True` | 是否启用 BM25 + 向量混合检索 |
| `rag_rrf_score_threshold` | `0.01` | RRF 融合分数过滤阈值 |

### MarkdownChunker 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `max_chunk_size` | `512` | child chunk 最大 token 数，超过则二级切分 |
| `min_chunk_size` | `64` | child chunk 最小 token 数，低于则跳过不索引 |
| `overlap_size` | `128` | 二级切分时相邻子 chunk 的重叠 token 数 |

### Retriever 内部常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `_RRF_K` | `60` | RRF 融合常数 k（标准值） |
| `_MULTI_HIT_ALPHA` | `0.15` | 多命中加成系数 α |
