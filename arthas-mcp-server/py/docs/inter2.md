# 简历项目描述（简洁版）

## 基于大模型的 Java 应用智能诊断平台

> 在分布式场景下，可观测性工具（trace/log/metric）能定位到出问题的服务，但服务内部的根因分析（CPU 飙高是哪个方法、内存泄漏是哪个对象、线程死锁在哪）仍依赖人工使用 Arthas 手动诊断。本项目将 Arthas 改造为 MCP Server 并构建 LLM 驱动的智能诊断 Agent，实现自动化编排诊断策略与根因定位。

### 一、Arthas MCP Server 改造（Java）

#### 反向连接架构
> 基于 Netty 实现 MCP 客户端，Agent 主动通过 WebSocket 外联管控平台（反向连接），使内网 JVM 应用无需暴露端口即可被远程管控。实现了 SSL 支持、认证鉴权、指数退避重连（5s→10s→20s...最大5min）、心跳保活与超时检测。

#### MCP 协议栈
> 手写完整 JSON-RPC 2.0 协议客户端，包括协议 Schema 定义、请求/响应处理器（处理 tools/list、tools/call、ping 请求，发送 initialize/notifications），支持 MCP 2025-06-18 协议版本。

#### 工具注解框架
> 设计 @Tool + @ToolParam 注解体系，通过反射扫描自动注册工具回调、运行时生成 JSON Schema，新增诊断工具只需编写一个带注解的方法。

#### 幂等与会话管理
> 基于 ConcurrentHashMap.putIfAbsent 对 taskId+stageId 做进程内执行权互斥，防止管控平台重发时工具被重复执行。管理 MCP Session → Arthas Session 的映射，支持会话过期检测（25min）与自动重建。

#### 诊断指令封装优化
> 统一 Arthas 同步/异步指令调用差异，精简返回内容、组合封装高阶指令，降低调用复杂度和 LLM Token 消耗。

#### APM 平台无感知集成
> 将 Arthas 能力嵌入 OpenTelemetry Java Agent，用户接入 APM 后即自动具备按需诊断能力，无需额外部署。

---

### 二、智能诊断管控平台（Python）

#### 事件驱动状态机
> 设计 Stage 事件驱动架构（USER_QUERY → LLM_THINKING → TOOL_CALL → TOOL_RESULT → LLM_CONCLUSION），每个 Stage 独立持久化，支持故障恢复——进程重启后从 DB 查询 running 任务的最新 pending stage 恢复执行。

#### 双驱动调度
> 轮询 + WebSocket 回调双驱动：定时扫 DB 取 pending stages 作为兜底（秒级延迟），WS 回调直接创建下一 stage 投递执行（毫秒级延迟），通过 TaskLock + stage 状态 double-check 保证互不冲突。支持链式执行——handler 返回 next_stage 后递归提交，无需等下次轮询。

#### 三层幂等保护
> 跨 Java/Python 层构建幂等体系：第一层 TaskLock 保证同一 task 不并发执行，第二层 handler 执行前重新加载 stage 检查状态，第三层 complete_and_next 在事务内再次检查。配合 Java 端进程内幂等，实现端到端执行安全。

#### 数据库设计
> 两张核心表 + 一张日志表。DiagnosisStage 唯一约束 task_id+stage_seq 防并发写入，包含审核三件套（支持高危命令拦截）、冷却控制（防重复发送）、摘要元数据（支持上下文优化回溯）、重试控制。complete_and_next 在同一事务中原子完成当前 stage + 创建下一 stage + 更新 task 序号。

#### 分布式锁
> 抽象接口 + 工厂模式，根据配置自动切换本地锁或 Redis 分布式锁。Redis 锁基于 SET NX EX 原子获取、Lua 脚本原子释放（校验 owner 防误释放）、Watchdog 看门狗按 TTL/3 自动续期。Redis 故障时快速失败不阻塞业务。

#### 高危操作安全约束
> 对高风险 Arthas 命令实现审核拦截，stage 进入 PENDING_APPROVAL 状态等待人工审核通过后才执行。

### 三、智能诊断引擎

#### ReAct 决策引擎
> 基于 LLM 实现 Thought → Action → Observation 循环，支持 Function Calling + 文本 JSON Fallback 双模式解析。LLM 调用失败时降级为直接结论输出，设有最大工具调用次数限制防死循环。

#### 四层上下文优化管道
> L0 即时摘要：单条工具结果超阈值时 LLM 压缩。L1 Token 精确计数：tiktoken 动态计算 system prompt 实际 tokens 精确分配预算。L2 全文摘要：超预算时保留首尾消息不压缩，中间消息 LLM 摘要。L3 滑动窗口硬裁剪：保留首尾 N 条直接丢弃中间。设计了延迟持久化机制：摘要暂存 metadata，仅在 LLM 返回 tool_call（有后续）时才持久化，结束时丢弃，避免浪费和序号污染。

#### RAG 混合检索
> Vector + BM25 混合检索，RRF（k=60）融合排序。设计 Parent-Child 双层索引：child chunk 小粒度检索精准，返回 parent chunk 大粒度保证语义完整。多命中加成公式聚合 parent 分数。支持异常自动降级。

# 面试官追问与刁难分析

> 以下从面试官角度出发，分析看到上述简历后**最可能从哪些角度发问和刁难**。分为"正常追问"和"刁难型追问"两类。

## 一、架构层面（必问）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| 整体架构是怎样的？ | Java 层做底层诊断能力（MCP Server + Arthas 指令），Python 层做智能编排（状态机 + LLM 决策），两层通过 WebSocket 通信 |
| 为什么要拆成 Java + Python 两层？ | Arthas 本身是 Java Agent，诊断能力必须在 JVM 内；Python 层贴近 LLM 生态，tiktoken / OpenAI SDK / 向量库等生态完善 |
| 为什么用 WebSocket 而不是 HTTP？ | 诊断是多轮交互（发指令 → 等结果），WS 天然支持服务端推送。HTTP 只能轮询，延迟高 |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **反向连接本质就是长连接，和普通 WS 有什么区别？你为什么把它叫"反向"？** | 传统模式是管控平台主动连接被管节点，要求被管节点暴露端口。反向是 Agent 主动连管控平台，管控平台只需暴露一个 WS endpoint。区别不在协议层，在于**连接发起方向反转**了，这是内网穿透场景的标准做法 |
| **Java 和 Python 之间如果 WS 断了，正在执行的诊断任务怎么办？** | 每个 stage 持久化在 DB，WS 断连只影响 TOOL_CALL 的发送。重连后 EventScheduler 轮询会重新拿到 pending stage 重发。Java 端幂等保证不重复执行 |
| **你说支持故障恢复，但如果 Python 进程崩了、DB 里的 pending stage 状态是脏的怎么办？** | 不会脏。stage 状态转换走的是 complete_and_next 事务——要么原子完成（当前 stage COMPLETED + 新 stage PENDING），要么 rollback 保持 PENDING。崩溃时要么事务已提交，要么 rollback，不存在中间状态。启动时对超时未完成的任务做 mark_failed 清理 |

## 二、MCP 协议改造（差异化优势，面试官会深挖）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| 为什么不用官方 MCP SDK？ | 当时 Java SDK 不成熟，且只支持 Server 等连模式。我们需要反向连接（Client 主动连），所以基于 Netty 手写。协议核心是 JSON-RPC 2.0，自己实现可控性更强 |
| MCP 协议核心是什么？ | JSON-RPC 2.0 的请求/响应/通知模型。核心接口是 tools/list（工具发现）和 tools/call（工具调用）。在此之上有 initialize 握手、capabilities 协商 |
| 指数退避重连的参数怎么确定的？ | 初始 5s，倍增到最大 5min。5s 足够短不影响体验，5min 封顶避免无意义重试浪费资源。成功连接后 reset |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **你说统一转 String 解决 id 类型不匹配，那 JSON-RPC 2.0 规范里 id 字段的类型定义是什么？** | 规范定义 id 可以是 String、Number 或 Null。但 Jackson 反序列化数字时可能得到 Integer 或 Long（取决于值大小），而发送端存的是 Long。`Long.equals(Integer)` 永远 false。统一转 String 是最安全的做法 |
| **MCP 协议你说 2025-06-18 版本，这个版本相对之前有什么变化？** | （需要你自己补充，比如 Streamable HTTP 传输、Elicitation 等新特性。如果记不清，可以说"主要是传输层的增强和新能力协商机制"） |
| **Netty Pipeline 里 IdleStateHandler 的超时值怎么确定的？和心跳间隔是什么关系？** | 读空闲超时 > 心跳间隔。心跳间隔 N 秒发一次 ping，读空闲超时设为 2-3 倍心跳间隔。如果连续 2-3 个心跳周期没收到任何数据，判定连接失效触发重连 |

## 三、幂等保护（工程能力的核心体现，必问）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| 为什么需要三层幂等？一层不够吗？ | 单层有漏洞。TaskLock 防并发，但锁释放后到 complete_and_next 之间可能有新调度进来；DB 层检查是最后一道防线，保证最终一致性。三层各有职责、层层递进 |
| Java 端的 putIfAbsent 和 Python 端的 TaskLock 有什么区别？ | Java 端保护的是**同一个 JVM 内**的工具不被重复执行（进程内互斥）。Python 端保护的是**同一个 task 不被并发调度**（可跨进程，用 Redis 锁） |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **如果三层保护都通过了，但在 complete_and_next 事务提交的瞬间进程崩了，会怎样？** | 事务要么提交要么 rollback。如果提交了，状态正确。如果 rollback，stage 仍为 PENDING，下次轮询会重新执行——但工具可能已经在 Java 端执行了一次。所以 Java 端的 TaskStageTracker 是最终兜底：即使 Python 端重发，Java 端 putIfAbsent 判定已执行则返回缓存结果 |
| **putIfAbsent 用的是 ConcurrentHashMap，进程重启后 Map 清空了，不就失去幂等能力了吗？** | 是的，这是设计取舍。JVM 重启意味着 Arthas session 也丢了，需要重新建立连接和会话。重启后的请求本质上是"新的执行"，不是重复执行。进程内幂等保护的是**进程生命周期内**的重复请求 |
| **你说 stage 用唯一约束 (task_id, stage_seq) 防重复写入，但 stage_seq 是怎么生成的？有没有可能两个并发写入拿到同一个 seq？** | seq 从 task.current_stage_seq + 1 获取，complete_and_next 在事务内原子更新 task.current_stage_seq。两个并发写入在 DB 唯一约束上会有一个报 IntegrityError，被上层捕获后安全退出 |

## 四、分布式锁（经典八股延伸，必问）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| Redis 锁为什么需要 Lua 脚本？ | 释放锁时必须校验 owner——先 GET 判断是不是自己的，再 DEL。这两步必须原子执行，否则在 GET 和 DEL 之间锁可能过期被别人抢了 |
| 看门狗为什么 TTL/3？ | 给两次续期容错。每 TTL/3 续期一次，TTL 内有 3 次机会。即使一次续期失败（网络抖动），还有 2 次机会 |
| Redis 挂了怎么办？ | acquire 返回 False（快速失败），调度器下次轮询重试，不阻塞业务流程 |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **Redis 单点锁有什么问题？你知道 Redlock 吗？为什么没用？** | 单点 Redis 主从切换时可能丢锁（主节点写入还没同步到从节点就挂了）。Redlock 需要 5 个 Redis 实例，复杂度过高。我们的场景是诊断任务（不是金融交易），偶尔的锁丢失通过 stage 状态 double-check 兜底，可以接受 |
| **如果看门狗续期成功，但业务逻辑 hang 住了，锁永远不释放怎么办？** | 看门狗会一直续期直到进程崩溃或被强制 cancel。但业务层面有 task 超时检测——EventScheduler 扫描 running 时间过长的 task 做 mark_failed。所以不会真的"永远"不释放 |
| **asyncio.Lock 在多线程环境下安全吗？** | asyncio.Lock 只在同一个事件循环内有效，不是线程安全的。但我们的管控平台是单进程异步架构（asyncio），不存在多线程竞争。多实例场景用 Redis 锁 |

## 五、上下文管理（最有技术深度，高级面试官会考）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| 为什么不直接截断？ | 截断丢失关键诊断线索，LLM 会重复调用相同工具浪费 Token。摘要能保留核心结论 |
| 为什么动态计算 system prompt tokens？ | system prompt 包含工具列表和 RAG 检索结果，每次推理都不同。静态预留要么浪费预算要么不够 |
| 延迟持久化解决什么问题？ | 避免在诊断结束时多出一条无意义的 CONTEXT_SUMMARY stage，保持事件时间线干净 |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **LLM 摘要本身会丢失信息，你怎么保证摘要后 LLM 的诊断质量不下降？** | 摘要 prompt 明确要求保留诊断线索、异常值和工具调用结论。实际效果上，丢失的是原始数据细节（如 thread dump 的具体栈帧），保留的是"线程 XXX 死锁在 YYY"这种结论。如果摘要质量不够，L3 滑动窗口是 fallback，保留最近的原始消息确保最新上下文完整 |
| **你的四层管道是顺序执行还是可以跳过？如果 L0 摘要后还是超预算，L2 会重复摘要已经摘要过的内容吗？** | L0 处理的是单条工具结果（写入 summarized_content），L2 读取时优先使用 summarized_content。所以 L2 看到的中间消息已经是 L0 压缩后的版本，不会重复摘要原始内容 |
| **Token 计数用 tiktoken，但不同模型的 tokenizer 不同，你怎么处理？** | tiktoken 支持按模型名查找编码器（如 cl100k_base 对应 GPT-4）。如果模型不在已知列表，降级用 cl100k_base 做近似计数。精确性足够用于预算分配 |

## 六、RAG（常见但容易被深挖）

### 正常追问
| 问题 | 回答要点 |
|------|---------|
| 为什么混合检索？ | 向量检索擅长语义匹配，BM25 擅长关键词精确匹配。"线程死锁"这种术语 BM25 更准，"应用变慢了"这种模糊描述向量更准 |
| RRF 相比 score 加权好在哪？ | 不同检索源 score 不可比（余弦相似度 0.8 和 BM25 分数 15 没法直接加），RRF 只用排名融合，跨源公平 |
| Parent-Child 解决什么问题？ | 小 chunk 检索精准但语义不完整，大 chunk 语义完整但检索噪声大。Child 检索 + 返回 Parent，兼顾两者 |

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **RRF 的 k=60 是怎么来的？调成 20 或 100 会怎样？** | k=60 是论文原始推荐值。k 越小排名靠前的权重越大（极端化），k 越大排名差异被拉平。60 是经验平衡点。实际调参需要根据检索集大小微调，我们的文档量不大，60 够用 |
| **你的聚合公式 max(child_scores) + α×(hit_count-1)/total_children，为什么用 max 而不是 sum？** | sum 会让"子 chunk 多但每个匹配度一般"的 parent 分数虚高。max 确保 parent 的基础分是最相关的那个 child 贡献的，多命中只是加成（α=0.15 控制幅度） |
| **如果运维知识库更新了，向量索引怎么增量更新？** | （需要你自己补充：是全量重建还是增量 upsert？Chroma 支持 add/update，实际项目中怎么做的？） |

## 七、状态机与调度（系统设计能力，高级面试必考）

### 刁难型追问
| 问题 | 回答要点 |
|------|---------|
| **你说轮询 + WS 双驱动，但轮询有延迟。你有没有测过实际诊断一次端到端需要多久？瓶颈在哪？** | 瓶颈在 LLM 推理（2-5s/次），不在调度延迟。WS 回调路径是毫秒级，轮询只是兜底。端到端时长 = LLM 推理次数 × 单次推理时间 + 工具执行时间 |
| **为什么不用消息队列？** | 诊断任务量不大（不是高吞吐场景），MQ 增加部署复杂度。DB 轮询 + WS 回调已经满足需求，秒级兜底延迟可接受 |
| **链式执行在锁内还是锁外？如果在锁内，一个 task 的多个 stage 会长时间占锁？** | 锁外。handler 返回 next_stage 后先释放锁，再递归提交到 TaskPool。下一个 stage 执行时重新竞争锁。所以锁粒度是单个 stage，不是整个链 |
