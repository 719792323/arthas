## 你现在的困惑根源

之前的讨论很发散，你其实是被**多个层面的评估混在了一起**搞混了。让我帮你解耦：

```
你脑子里混在一起的其实是三件不同的事：

① 评估"一次 LLM 调用"         → 微观层面
② 评估"一个完整诊断任务"       → 宏观层面
③ 评估"系统中某个组件"（RAG/压缩/Prompt） → 归因层面
```

这三件事需要的输入数据是**不一样的**。我来分别讲清楚。

## 一、搞清楚你到底要评估什么

```
┌───────────────────────────────────────────────────────────────────┐
│                     你需要做的评估（按优先级排）                     │
├───────────────────────────────────────────────────────────────────┤
│                                                                   │
│  🥇 最重要：诊断结果对不对？                                       │
│     → "用户问 CPU 100%，系统最终说是死循环，这个结论对吗？"         │
│     → 这是端到端评估，评的是整个诊断任务                            │
│                                                                   │
│  🥈 次重要：过程合不合理？                                         │
│     → "它选的工具对吗？步骤冗余吗？推理逻辑连贯吗？"                │
│     → 这是轨迹评估，评的是 ReAct 过程                              │
│                                                                   │
│  🥉 再次要：哪个环节拖后腿？                                       │
│     → "结论错了，是 RAG 检索的锅还是 LLM 推理的锅？"               │
│     → 这是归因评估，用来定位系统瓶颈                                │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

**我的建议：先只做🥇，搞定了再做🥈，最后才做🥉。** 不要一上来就想做归因，那太复杂了。

## 二、🥇 端到端评估（最重要，先做这个）

### 输入什么数据？

**只需要 3 样东西**：

| 序号 | 数据 | 说明 | 从哪来 |
|------|------|------|--------|
| ① | 用户问题 | 用户一开始问了什么 | `Task.user_query` |
| ② | 最终结论 | 系统最后给出的诊断结论 | 最后一个 `conclude` 类型的 Stage |
| ③ | 参考答案（可选） | 这个问题的标准答案 | 你人工标注的 Benchmark |

```
给裁判的输入：

[System Prompt]
你是一个 Java 诊断专家。请评估 AI 系统给出的诊断结论是否正确。
打分 1-5 分：
- 5分：根因完全正确，定位到具体方法/代码行
- 4分：根因方向正确，但不够精确
- 3分：根因大致正确，但有遗漏
- 2分：根因方向有偏差
- 1分：根因完全错误
输出 JSON：{"score": <1-5>, "reason": "..."}

[User Prompt]
用户问题：线上服务 CPU 100%，请排查
系统结论：DataProcessor.processLoop() 第142行存在死循环，导致 Thread-42 持续占用 95.2% CPU
参考答案：DataProcessor.processLoop:142 死循环（如果有的话）
```

**就这么简单。** 不需要传 RAG 内容，不需要传 context 快照，不需要传压缩记录。因为你现在只关心 **"最终答案对不对"**。

### 这样做的好处

- 输入简单，token 消耗小
- 可以大规模跑（每次诊断都评估）
- 足够发现系统的主要问题
- 如果最终结论大部分都是对的，你根本不需要做更深层的评估

---

## 三、🥈 轨迹评估（端到端做完后再做）

### 什么时候需要？

当你发现 🥇 的评分很低，你想知道 **"到底是哪一步走错了"**。

### 输入什么数据？

在 🥇 的基础上，多加一样东西：**完整的诊断过程**。

| 序号 | 数据 | 说明 |
|------|------|------|
| ① | 用户问题 | 同上 |
| ② | **完整诊断轨迹** | 每一步的 thinking + 工具调用 + 工具返回 + 结论 |
| ③ | 最终结论 | 同上 |
| ④ | 参考答案（可选） | 同上 |

```
给裁判的输入：

[System Prompt]
你是诊断质量评审专家。请从以下维度评估诊断过程...
（评分维度：策略合理性、推理质量、工具使用效率、结论准确性）

[User Prompt]
## 用户问题
CPU 100% 请排查

## 诊断过程
Round 1: 
  思考：需要查看 CPU 最高的线程
  工具：thread -n 3
  结果：Thread-42 CPU 95.2%, GC-Thread 3.1%

Round 2:
  思考：Thread-42 异常，查看堆栈
  工具：thread 42
  结果：at DataProcessor.processLoop(DataProcessor.java:142) ...

Round 3:
  思考：堆栈显示 processLoop 死循环
  结论：DataProcessor.processLoop:142 死循环

## 参考答案（如果有）
...
```

**注意：这里的诊断轨迹是从你数据库 Stage 表中拼接出来的原始真实数据，不是 context manager 传给 LLM 的版本。** 裁判要看的是"上帝视角"——真实发生了什么。

## 四、🥉 归因评估（确认系统有问题后再做）

### 什么时候需要？

当你发现某类问题诊断效果一直不好，你需要搞清楚 **"是 RAG 的锅还是 LLM 的锅还是 Prompt 的锅"**。

### 输入什么数据？

在 🥈 的基础上，再多加几样东西：

| 序号 | 数据 | 说明 | 目的 |
|------|------|------|------|
| ⑤ | RAG 检索结果 | 检索了哪些文档，相似度多少 | 判断"检索的锅？" |
| ⑥ | 实际 context 快照 | 最后一轮 LLM 实际收到的 messages | 判断"context 丢信息了？" |
| ⑦ | 压缩记录 | 哪些内容被摘要了 | 判断"压缩策略的锅？" |
| ⑧ | System Prompt | 给 LLM 的指令原文 | 判断"Prompt 的锅？" |

**这个级别的评估不需要每次都做**，只在排查问题时才用。

### 归因评估的 Input 举例

归因评估不是一个大而全的 Prompt，而是**针对不同归因方向分别设计裁判输入**。以下是三个子场景的具体举例：

#### 场景 A：RAG 检索归因 —— "检索到的文档有用吗？"

```
给裁判的输入：

[System Prompt]
你是一个信息检索质量评估专家。请判断：给定用户问题，RAG 系统检索到的文档是否
包含了解决该问题所需的关键信息。

评估维度：
- 相关性（0-5）：检索结果与问题的匹配程度
- 充分性（0-5）：检索结果是否包含足够的诊断知识来得出正确结论
- 噪声（0-5）：检索结果中无关信息的多少（5=无噪声）

输出 JSON：{"relevance": <0-5>, "sufficiency": <0-5>, "noise": <0-5>, "reason": "..."}

[User Prompt]
## 用户问题
应用出现 OOM，帮我排查

## 系统最终给出的（错误的）结论
建议增大 JVM 堆内存 -Xmx 参数

## 参考正确答案
应使用 heapdump 导出堆快照，分析 com.example.CacheManager 中的 HashMap 持续增长导致内存泄漏

## RAG 实际检索到的文档
文档1 (相似度 0.85): "Arthas memory 命令可以查看 JVM 内存使用情况，包括堆内存、非堆内存..."
文档2 (相似度 0.78): "JVM 启动参数 -Xmx 用于设置最大堆内存大小，-Xms 用于设置初始堆内存..."
文档3 (相似度 0.72): "常见 JVM 性能调优参数列表..."

## 知识库中实际存在但未被检索到的相关文档（如果已知）
"Arthas heapdump 命令可以导出堆快照，配合 MAT 分析内存泄漏..."
"OOM 排查 SOP：第一步 heapdump，第二步分析大对象，第三步定位泄漏点..."

请评估 RAG 检索质量。
```

**这个例子的评估结论**：RAG 检索到的都是"内存参数配置"类的文档，没有检索到"heapdump 排查内存泄漏"的关键文档 → **归因：RAG 检索的锅**（可能是 query 改写不好，或知识库向量化有问题）。

#### 场景 C：Prompt/LLM 推理归因 —— "给了足够信息，LLM 还是推理错了？"

```
给裁判的输入：

[System Prompt]
你是一个 AI 推理能力评估专家。
以下场景中，LLM 已经获得了足够的信息来做出正确诊断，
请判断 LLM 的推理过程是否存在逻辑错误。

评估维度：
- 信息利用（0-5）：LLM 是否充分利用了已有线索
- 推理逻辑（0-5）：推理链条是否正确
- 结论合理性（0-5）：最终结论是否与已知信息一致

输出 JSON：{"info_utilization": <0-5>, "reasoning_logic": <0-5>, "conclusion_quality": <0-5>, "reasoning_error": "具体推理错误描述", "reason": "..."}

[User Prompt]
## 用户问题
服务出现大量超时

## LLM 实际收到的完整 context（确认信息充足）
System Prompt: 你是 Arthas 诊断助手，擅长 Java 应用诊断...

历史对话:
- thread -n 5 结果：Thread-pool-executor-3 BLOCKED, Thread-pool-executor-7 BLOCKED, Thread-pool-executor-12 BLOCKED
- thread --state BLOCKED 结果：共 38 个 BLOCKED 线程，全部阻塞在 com.example.OrderService.lock (OrderService.java:89)
- monitor -c 5 com.example.OrderService processOrder 结果：avg RT = 12543ms, total=5, fail=3

## LLM 的推理过程
"观察到多个线程处于 BLOCKED 状态，平均响应时间 12.5 秒。
这可能是由于网络延迟或下游服务响应慢导致的。
建议检查网络连接和下游服务的健康状态。"

## 参考正确答案
38个线程全部阻塞在 OrderService.java:89 的锁上，这是典型的锁竞争/死锁问题，
应该用 thread -b 命令查看阻塞源，而不是归因为网络问题。

请评估 LLM 的推理质量。
```

**这个例子的评估结论**：LLM 已经看到了"38个线程 BLOCKED 在同一个锁上"这个明确的锁竞争证据，但错误地归因为网络问题 → **归因：LLM 推理能力的锅**（不是 RAG 的问题，也不是 Context 压缩的问题，是 LLM 自身推理能力不足或 Prompt 中缺少锁竞争场景的引导）。

---

### 归因评估小结

| 归因方向 | 裁判核心问题 | 如果得分低说明... |
|---------|------------|----------------|
| **RAG 检索** | 检索到的文档与解决问题相关吗？ | 知识库缺文档 / 检索策略有问题 |
| **Context 压缩** | 压缩过程丢失了关键诊断线索吗？ | 压缩策略太激进 / 摘要质量差 |
| **LLM 推理** | 给了充足信息，LLM 的推理逻辑对吗？ | 模型能力不足 / Prompt 引导不够 |

**归因评估的核心思路**：通过控制变量法，每次只评估一个环节，判断"如果这个环节做对了，最终结论会不会变好？"

## 六、一张表总结

| 评估层级 | 输入数据 | 频率 | 复杂度 | 价值 |
|---------|---------|------|--------|------|
| **🥇 端到端** | 用户问题 + 最终结论 + 参考答案 | **每次诊断都跑** | ⭐ 简单 | 知道"系统好不好" |
| **🥈 轨迹** | 上面 + 完整 ReAct 过程 | 低分 Case 才跑 | ⭐⭐ 中等 | 知道"哪步出了错" |
| **🥉 归因** | 上面 + RAG/Context/Prompt 等 | 排查时才用 | ⭐⭐⭐ 复杂 | 知道"该改哪个模块" |

---

**所以回到你的问题——"评估到底应该输入什么数据"：**

> **答案是：先只输入"用户问题 + 最终结论"，这就够了。** 不要一上来就想把 RAG、context 快照、压缩记录全部塞进去。那是在你确认系统有问题、需要精确定位时才需要的东西。先把最简单的端到端评估跑起来，再逐步深入。
