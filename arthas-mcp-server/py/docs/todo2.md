## 一、你提到的问题分析

### 1. 循环调用问题 ✅ 非常合理

**场景**：LLM 在某个工具调用失败后，不断重试同一个工具，或者在 A → B → A → B 之间来回调用，形成死循环。

比如从日志中就已经看到了类似现象：`trace` 超时后，LLM 尝试 `watch`，`watch` 也失败，又尝试 `trace`...

**建议方向**：
- 记录每个 task 中已调用过的工具 + 参数组合，如果完全相同的调用出现 N 次，自动终止并给出结论
- 在构建 LLM prompt 时，明确告知"以下工具调用已经失败过，请勿重复尝试"

### 2. 最大轮次还没有给出结果 ✅ 非常合理

**场景**：LLM 不断调用工具收集信息，但迟迟不给出 `conclude`，最终达到最大轮次限制后，任务被强制终止，用户看不到任何结论。

**建议方向**：
- 达到最大轮次时，不应简单地标记 `failed`，而是应该**强制触发一次总结**：把已收集到的所有信息塞给 LLM，要求它"基于目前已有的信息给出你的最佳判断"
- 可以设一个"软限制"（如 8 轮）提醒 LLM "请尽快给出结论"，和一个"硬限制"（如 12 轮）强制总结

### 3. 上下文过大 ✅ 非常合理

**场景**：随着工具调用增多，历史 messages 越来越长，尤其是工具返回结果（如 `thread` 的完整 JSON）可能非常大，最终超出模型的 context window 或导致推理质量下降。

**建议方向**：
- **工具结果摘要化**：不要把原始 JSON 全部塞进上下文，而是提取关键信息（如"3 个线程 CPU > 97%，均在 `Case1.cpuIntensiveTask`"）
- **滑动窗口**：只保留最近 N 轮的完整对话，更早的轮次只保留摘要
- **token 计数**：在构建 prompt 时实时估算 token 数，超过阈值时自动压缩历史

### 4. 诊断没方向，大量调用无用命令 ✅ 非常合理

**场景**：LLM 对问题缺乏理解，盲目调用各种工具"碰运气"，浪费时间和资源。

**建议方向**：
- 在 system prompt 中给出**诊断策略模板**（如 CPU 问题先用 thread → jad，内存问题先用 heapdump → memory 等）
- 记录工具调用的"有效性"（是否返回了有价值的信息），如果连续 N 次调用都无有效结果，强制进入总结阶段

## 二、我认为还需要关注的问题

### 5. 🔒 并发安全 / 同一会话多任务冲突

当同一个 session 上有多个诊断任务同时运行时，工具调用可能互相干扰。比如一个任务在 `trace`，另一个任务也发 `trace`，Arthas 端可能会冲突。之前的 "Stage is already executing" 错误就是这类问题的体现。

**建议**：同一 session 的诊断任务应该串行执行，或者至少在工具调用层面做互斥锁。

### 6. 🧠 LLM 幻觉 / 错误推理

LLM 可能对工具返回的结果做出错误解读，比如把正常的线程误判为问题线程，或者编造不存在的类名去调用 `jad`。

**建议**：
- 对 LLM 生成的工具参数做基本校验（如类名格式是否合法）
- 在结论阶段可以加一个"置信度"字段，让 LLM 自评

### 7. ⏱️ 工具调用超时策略分化

不同的工具有不同的特性，不应该用统一的超时时间：
- `jad`、`sc`、`sm` 这类查询型命令应该很快返回（5-10s）
- `trace`、`watch`、`profiler` 这类需要等待触发的命令可能需要更长时间（30s-60s）
- `heapdump` 可能需要几分钟

**建议**：按工具类型配置不同的超时时间。

### 8. 🔄 诊断任务的可恢复性

如果管控平台进程重启了，正在执行中的诊断任务怎么办？目前 stage 状态存在数据库里，但进程重启后，内存中的执行上下文（如 WebSocket 连接、pending 的工具响应）都丢失了。

**建议**：
- 重启后扫描 `running` 状态的 stage，标记为 `failed` 或 `timeout`
- 如果 session 还在，可以尝试从断点恢复

### 9. 💰 成本控制

每次 LLM 调用都有 token 成本，如果一个诊断任务跑了 10+ 轮，且每轮的 prompt 都包含大量历史上下文，成本会快速累积。

**建议**：
- 记录每个 task 的总 token 消耗（prompt_tokens + completion_tokens），你现在已经有 prompt log 了，可以做统计
- 设置单个任务的 token 上限

### 10. 📊 诊断质量评估

目前没有机制评估诊断结论的质量。长期来看需要建立反馈闭环。

**建议**：
- 在 timeline API 的结论阶段加一个用户反馈字段（有用 / 无用 / 部分有用）
- 记录典型场景的诊断路径，作为后续优化 prompt 的参考
