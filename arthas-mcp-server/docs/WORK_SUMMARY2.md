## Java 应用二级诊断（面向 APM 用户）

### 一句话定位
- 在 APM 的 trace/metric/log 将问题缩小到“可疑服务/实例”后，提供 **JVM 级二级下钻**（Arthas）并通过平台化编排实现**远程、按需、可控、可回放**的自动化诊断。

### 端到端方案（我负责的核心能力）

#### 1）内网无暴露端口的远程管控：反向连接 + MCP 协议通道
- 设计并实现 **Agent 主动外联到管控平台**的反向连接（FastAPI `WebSocket /mcp`），实例无需开放诊断端口即可接入。
- 实现 **会话管理与心跳检测**：基于 MCP `ping` 定时探活，连接替换/超时清理，保证长连接稳定性。
- 支持接入侧鉴权：`Bearer` Token 校验，避免未授权实例接入。

#### 2）诊断任务引擎：事件驱动状态机 + 落库可恢复 + 并发/幂等控制
- 设计并落地 **Stage 状态机**（`USER_QUERY → LLM_THINKING → TOOL_CALL → TOOL_RESULT → ... → LLM_CONCLUSION`），每个 stage 独立持久化，进程重启可从 DB 恢复。
- 实现“轮询兜底 + 回调加速”的执行模型：
  - 调度器轮询拾取 `pending` stage 投递到执行池；
  - 同时支持工具异步返回的 WS 回调驱动：从响应 `_meta` 提取 `task_id + stage_seq`，在锁+事务保护下推进到下一 stage，并立即投递执行池减少等待。
- 引入 **任务锁抽象**（本地锁 / Redis 分布式锁可切换），统一 `async with task_lock.locked(task_id)` 约束同一任务全局互斥，结合 stage 状态检查实现幂等（重复响应/重复投递不会重复推进）。

#### 3）Arthas 能力工具化：面向自动化/LLM 的指令封装与结果治理
- 抽象 Arthas 指令调用（同步/异步差异、超时、错误返回），对上层提供一致的工具调用接口。
- 对命令输出做**裁剪与结构化**，并在平台侧记录 `tool_name/tool_arguments/tool_result/raw_response`，兼顾诊断有效性与 token 成本。

#### 4）生产可控：高风险命令审核 + 任务治理
- 建立高风险命令的 **waiting_approval → approve/reject** 审核链路；reject 自动创建新的 `LLM_THINKING` stage 让策略重新决策，避免直接在生产执行危险操作。
- 提供任务终止/删除的安全约束：删除任务前必须获取任务锁，避免删除正在执行的任务；启动时检测并标记“卡住”的历史任务，保证系统自愈。

#### 5）可观测与可回放：时间线与对话复现
- 提供任务时间线视图（按 `stage_seq` 渲染每一步推理/工具调用/结果/结论）。
- 支持从 DB 复现“实际发给 LLM 的 messages”（含工具调用与 tool result），用于审计、复盘与问题定位。

#### 6）APM 无感集成：OTel Java Agent 按需加载 Arthas
- 将二级诊断能力嵌入 **OpenTelemetry Java Agent**：用户接入 APM 后即具备“按需诊断”能力。
- 服务端触发诊断流程，实现“需要时启用、用完即收”，降低额外部署与运维成本。

### 价值（面向面试可量化的点）
- **缩短定位链路**：从“怀疑某服务/实例”推进到“定位到线程/方法/锁竞争/类加载问题”的可执行证据。
- **生产可用**：无端口暴露、可鉴权、可审核、可恢复、可回放；同时通过输出治理降低对 JVM 与大模型 token 的额外成本。

面试时最容易被追问、你必须准备的点
量化：并发上限（pool）、轮询间隔、平均诊断耗时、成功率、重连率、输出裁剪后 token 节省比例、对 JVM 的扰动控制策略。没数字就会被当“描述型项目”。
安全边界：你已经做了“审核链路”，面试官会追问：哪些命令需要审核？审计怎么做？拒绝后如何避免 LLM 无限重试同一高危命令？
故障场景：WS 断线、重复响应、平台重启、DB/Redis 不可用时行为是什么（你现在的架构是能讲清楚的）。
